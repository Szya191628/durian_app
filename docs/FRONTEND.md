# 榴夏来榴莲生鲜前端重构说明

## 1. 产品需求与页面结构

目标是原生微信生态内的榴莲零售体验：顾客快速挑选品种、核对规格、加购、下单和跟踪订单；店铺管理商品及发货。使用现有云数据库与 8 个云函数，不另造商品、优惠、销量或真实支付能力。

保留 17 个路由。底部导航为首页、购物袋、我的；分类和商品详情承接选购；订单确认后 redirect 到详情，减少重复返回。管理端从「我的」进入，分为工作台、商品列表/编辑、订单列表/详情。

| 模块 | 页面 | 主要交互 |
| --- | --- | --- |
| 选购 | home、category、detail | 品种筛选、关键词确认搜索、分页、规格、数量、加购、直接购买 |
| 交易 | cart、order-confirm | 勾选、批量结算、地址选择、金额核对、订单确认弹窗、提交锁 |
| 订单 | order-list、order-detail | 状态筛选、物流单号复制、订单进度、收货确认、微信客服 |
| 账户 | mine、login、member | 账户资料、订单数量、余额、积分、会员说明 |
| 地址 | address-list、address-edit | 分页、默认地址、编辑、删除、地区选择、字段校验 |
| 管理 | admin/index、products、product-edit、orders、order-detail | 管理员入口、数据概览、图片上传、商品上下架、物流和发货 |

信息架构为「一级入口 → 二级列表 → 三级内容/操作」。微信原生导航栈在跨流程访问时可能超过三个实例，例如从结算页打开地址编辑；此处的三级指产品信息层级，不是强行限制所有页面栈长度。

## 2. UI 布局与交互

采用奶油浅底、深绿色与榴莲金。危险状态单独使用语义红色。系统中文字体保证首屏无需下载字体；数字采用独立数字字体栈。首页用品牌配图建立食欲与商品语境，真实商品图片缺失时显示「商品图片待补充」，不把品牌图当作实拍。

- 顶部导航：从窗口、状态栏和微信胶囊测量真实位置，转换为 rpx。胶囊区域留白，保留原生底部 TabBar。
- 首页：搜索 → 品牌视觉 → 功能提示 → 实时在售商品数 → 商品目录 → 品种入口；先展示商品，缩短从打开首页到加购的路径。
- 商品卡：品种、名称、规格、价格、售罄/低库存状态、单步加购。详情页突出价格与规格，并补充规格包装、配送和售后说明，购买动作固定底部。
- 购物袋：选择、数量与金额同步更新，删除先确认；直接购买结算不会误清购物袋。
- 表单：持续标签、逐字段错误、长度/金额/库存校验、提交锁、成功提示。确认订单页同时展示商品件数、配送费用确认方式和生鲜售后提示。
- 状态：初次请求骨架屏；失败展示原因与重试；空状态提供下一步；列表分页失败保留已加载结果。
- 动效：100ms 按压、200ms Tab 指示线、250ms 内容渐入；只使用 opacity / transform；降低动态偏好关闭位移动画。
- 安全区域：底部操作栏补齐 env(safe-area-inset-bottom)，内容预留操作栏空间。

列表才进行上拉分页；登录、本地购物袋、详情和编辑表单没有虚假的「加载更多」。全部页面开启下拉刷新，异步刷新完成后再关闭原生指示器；本地页面同步更新。

## 4. 代码组织

代码已经逐文件写入工程，可以直接导入微信开发者工具；无需从文档中手工复制代码。WXML 只做展示与事件绑定，JavaScript 页面通过服务和 store 完成业务。

### 公共组件

| 组件 | 作用 |
| --- | --- |
| app-nav | 安全区域及胶囊适配、品牌标题、返回导航 |
| ui-icon | 统一图标与颜色规格 |
| data-card | 管理端/会员余额与数量数据展示 |
| info-row | 资料、订单记录和设置入口 |
| ui-tabs | 横向状态与品种切换 |
| search-box | 搜索输入、清空、确认及只读入口 |
| filter-menu | 原生 picker 下拉筛选 |
| app-modal | 带提交状态的确认弹窗 |
| page-state | 骨架屏、空数据、失败及重试 |
| list-footer | 分页加载、失败重试、结束提示 |
| product-card | 商品图、库存、价格与加购 |
| quantity-stepper | 数量边界与增减 |
| order-card | 商品清单、订单状态与详情入口 |

### 数据服务

`client.js` 集中处理云连接、读取超时、业务错误和网络错误。读取超时 15 秒；写操作不做自动重试，避免不确定结果下重复写入。创建订单出现无法确认的传输错误时，引导用户先检查订单列表。

`catalog.js` 对接 getProducts、getCategories；`user.js` 对接 login、updateUser；`orders.js` 对接订单查询及创建；`address.js` 对接地址 CRUD 与分页；`admin.js` 封装管理端现有数据库行为和图片上传。页面不直接使用 wx.cloud。

### 状态与计算

store 只维护需要跨页面共享的数据，使用订阅函数并在页面销毁时解除订阅。购物袋写入原有 `cart` 缓存键，兼容原字段，不持久化用户身份。公开读取返回快照，避免页面意外修改内部状态。

数据库历史金额单位为「元」，本次保持这个契约；前端求和先转换为整数分，再转回元展示。下单仅提交商品 ID 和数量，最终金额与库存由现有 createOrder 云函数核验。

已兼容初始化数据中的分类编码：猫山王→musang_king、金枕→golden_pillow 等。新增分类建议显式提供 `code` 字段；服务层优先使用该字段。

## 5. 验证与运行

无需安装根目录依赖即可运行：

```powershell
cd F:\durian-shop
npm run check
npm test
```

静态检查覆盖全部路由、四类页面文件、组件声明、JS/JSON 语法、样式引用及导航目标。测试覆盖金额、缓存、库存、购物袋结算、异步竞态、分页失败、生命周期、提交锁、输入校验、所有页面/组件事件，以及通过实际 services 运行 17 个页面的受控云数据加载。

浏览器预览使用实际 WXML/WXSS/组件模板转换，不是另写一套设计稿。商品、用户、订单、经营数量均为标明用途的测试样例，预览不接入生产数据，不具备真实业务交互。浏览器检查不能代替微信开发者工具编译、基础库兼容性测试和真机测试。

### 微信开发者工具联调

1. 导入此目录，填入 `project.config.json` 的真实 AppID。
2. 在 `config/index.js` 填写真实 `cloudEnv`。配置使用 JavaScript 模块，避免微信开发者工具将 `require('./config/index.json')` 解析成未注册模块，导致 `app.js` 启动失败、页面未注册和白屏。占位环境下页面明确展示店铺暂未连接。
3. 部署现有云函数并在云端安装各自 package.json 依赖；核查实际数据库与索引。不要在生产环境直接调用 initData。
4. 检查 products / orders / addresses 的查询索引。地址需支持用户归属、默认地址和创建时间排序；商品/订单分页可能需要按控制台反馈创建复合索引。
5. 配置数据库与云存储访问规则，绑定微信客服，上传真实商品图片。
6. 用独立测试环境验证加购、搜索筛选、地址、下单与发货。`enableTestPayments` 默认为 false；仅在隔离测试环境显式开启模拟支付及测试充值。
7. 在真机上验证 iOS / Android 的字体、胶囊、安全区、键盘、地区选择器、图片选择器和客服；建议使用支持 wx.chooseMedia 的基础库。

## 6. 后续扩展与当前边界

当前交付为前端重构，不表示后端已满足生产交易标准。现有后端接口保持不变，以下是上线前的实质性工作：

- **支付闭环**：接入真实微信支付、服务端回调验签、充值流水与订单幂等；现有 mock 下单和 recharge 都没有真实扣款校验。前端隐藏入口不能阻止直接调用云函数，必须在服务端禁止生产测试路径。
- **服务端权限**：管理端已有数据库直写，必须通过安全规则或带管理员鉴权的云函数限制；用户只可访问自己的订单/地址。前端 role 判断不构成安全边界。
- **订单一致性**：下单幂等键、库存预占/释放、重复商品合并、取消与退款状态机。现有云函数事务逻辑需要独立审计，前端本次没有改变它。
- **隐私及运营**：补齐真实隐私保护指引、平台隐私接口配置、售后规则、运费与配送规则、客服运营配置。没有编造政策链接或虚构电话。
- **商品内容**：后台新增真实图片上传能力；生产需完善文件类型/大小与资源权限校验、废弃图片清理。当前图片移除只移除表单引用，不删除云端文件。
- **能力扩展**：优惠券与营销必须由服务端定价；物流轨迹接正式物流接口；搜索排序与价格区间由服务端分页处理，不能只排序当前已加载的数据。
- **主题与工程**：当前为浅色主题；深色令牌预留但未开启系统自动切换。后续可增加 TypeScript、分包、错误监控、CI 真机自动化及分页数据窗口化。

本次不包含云端部署、真实支付接入和微信官方编译/真机测试。上线应以完成这些检查为准。
